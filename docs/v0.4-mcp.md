# V0.4-A: `find_evidence` as an external MCP tool

V0.4-A adds one thing on top of the stable V0.3.2 Evidence Engine: a read-only
MCP server that lets an external agent (Claude Code, Codex) call
`EvidenceReportService.build_report` directly, instead of a human running the
desktop app or `app.cli`.

No retrieval, ranking, evidence classification, citation tracing, paper
identity resolution or reference parsing was changed or reimplemented. The MCP
layer only validates input, calls the existing service, and reshapes its
already-classified, already-ranked `EvidenceReport` into a structured response.

## Architecture

```text
app/external_api/
  mcp_schemas.py   Public response schema (pydantic models) - no internal
                   Evidence Engine parameters are exposed here.
  mcp_adapter.py   find_evidence(query, top_k, evidence_types) - the only
                   place that calls EvidenceReportService.build_report;
                   validates input, filters/truncates after classification,
                   translates internal errors into typed MCP errors.
  mcp_server.py    FastMCP app; registers exactly one tool, `find_evidence`,
                   which delegates to mcp_adapter.find_evidence unchanged.
```

Call path:

```
external agent
  -> MCP find_evidence(query, top_k, evidence_types)
  -> app.external_api.mcp_adapter.find_evidence(...)
  -> app.evidence.report.EvidenceReportService.build_report(query)   # unchanged V0.3.2 pipeline
       -> EvidenceService.build_evidence_pack   (hybrid retrieval + passage dedup)
       -> paper_identity.resolve_identities     (paper-level dedup)
       -> classifier.classify_passage           (DIRECT/SECONDARY/LIMITING/CONTEXTUAL/UNCERTAIN)
       -> citation_tracer.trace_citations       (SECONDARY -> local primary source)
       -> ranker.rank                           (tiered ranking, never by raw score alone)
  -> mcp_adapter maps EvidenceReport -> mcp_schemas.FindEvidenceResult
```

The server is runnable independently of the PySide6 desktop GUI:

```powershell
.\.venv\Scripts\python.exe -m app.external_api.mcp_server
```

It talks MCP over stdio and does not need Zotero running to search an
already-indexed local library (same as `app.cli search`).

## `find_evidence` schema

Input:

```json
{
  "query": "string, required, non-empty",
  "top_k": "integer, default 10, 1-200",
  "evidence_types": ["DIRECT | SECONDARY | LIMITING | CONTEXTUAL | UNCERTAIN", "..."]
}
```

`top_k` is applied to the final, already-classified and already-ranked
evidence list - never reinterpreted as a raw retrieval candidate count.
`evidence_types`, when given, filters that same already-classified list;
filtering never happens before retrieval, so it cannot change which papers or
passages get retrieved in the first place.

Output (`FindEvidenceResult`): `query`, `evidence` (list of `EvidenceItem`),
`returned_count`, `total_classified_count` (before the `top_k` cut, after
`evidence_types` filtering), and `retrieval_summary`
(`candidate_count`, `duplicate_passages_removed`, `duplicate_papers_merged`).

Each `EvidenceItem` has:

- `evidence_id`, `evidence_class`, `classification_confidence`, `rationale`, `retrieval_score`
- `paper`: `canonical_id`, `title`, `authors`, `journal`, `year`, `doi`,
  `zotero_item_key` (the specific library record this passage came from),
  `zotero_item_keys_merged` (every Zotero record merged into this paper identity)
- `passage`: `text` (verbatim, unmodified), `pdf_page`
- `provenance`: `attachment_key`, `origin` (`original_retrieval` | `citation_tracing`), `parent_evidence_id`
- `citation_traces`: for SECONDARY evidence, each traced marker's parsed
  reference metadata, `resolution_status`, and the resolved local paper
  (`canonical_id`, `title`, `zotero_item_keys`) if any

Missing data is `null`, never fabricated.

## Errors

Any problem - empty query, out-of-range `top_k`, an unknown `evidence_types`
value, a local-database failure, a semantic-index failure, or an unexpected
Evidence Engine exception - raises a typed exception in `mcp_adapter`
(`InvalidQueryError`, `InvalidEvidenceTypeError`, `DatabaseUnavailableError`,
`EvidenceEngineError`). The MCP server does not catch these itself: the MCP
SDK's own tool-call handling turns any exception raised inside a `@mcp.tool()`
function into a structured `CallToolResult(isError=True, ...)` with the
exception message, so a failure is always visible as an error, never as a
silently empty `evidence: []`.

## Read-only guarantee

`find_evidence` only calls `EvidenceReportService.build_report`, which itself
only reads from `data/literature.db` and already-extracted PDF text. Nothing
in `app/external_api` writes to Zotero, `literature.db`, the semantic index,
or any PDF; no index rebuild is triggered.

## Connecting Claude Code

**See `docs/v0.4.1-mcp-connectivity.md` for the current, verified
`.mcp.json` and CLI registration steps.** The `cwd`-based example
previously shown here does not match the installed Claude Code MCP config
schema (no `cwd` field exists for stdio servers) and would fail to resolve
the `app` package unless launched from exactly the project root; V0.4.1
replaces it with an `env.PYTHONPATH`-based config, verified end-to-end.

Codex CLI supports the same `mcp_servers` concept in its own config format
(`~/.codex/config.toml`, `[mcp_servers.research-assistant-evidence]` with
`command`/`args`); this has not been verified in this environment, so treat it
as unconfirmed until tried against an actual Codex installation.

## Scope

V0.4-A intentionally ships only `find_evidence`. `get_source`,
`verify_citation`, `find_evidence_for_claim`, manuscript/introduction
generation, a local LLM, web search, journal ranking/impact factor, GUI or CLI
changes, and automatic Zotero mutation are all out of scope for this version.
