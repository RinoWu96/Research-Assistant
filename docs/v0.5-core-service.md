# Research Assistant Core Service (V0.5)

## Why

The V0.4/V0.4.1 MCP server constructed its own `EvidenceReportService`
(and therefore its own `UnifiedSearchService`/`LocalEmbedder`) inline, in
the MCP process. On a centrally managed Windows machine, a freshly spawned
Python process loading `sentence-transformers`/PyTorch under CrowdStrike
Falcon's real-time file scanning has been observed to take up to ~13
minutes before the embedder finishes loading. Every MCP restart (Claude
Code restart, tool reload, crash) paid that cost again, and there was no
way to keep the model warm across restarts, because the model lived
inside the process being restarted.

V0.5 moves the Evidence Engine's heavy resources into a separate,
persistent **Research Assistant Core Service** process. It loads the BGE
embedder once and keeps it in memory; MCP (and eventually the GUI and
local-LLM integrations) become thin clients that call it over localhost
HTTP and never construct any of it themselves.

## Architecture

```
Claude Code -> MCP find_evidence -> app.external_api.mcp_adapter (thin proxy)
                                          |
                                          v  HTTP, 127.0.0.1 only
                              Research Assistant Core Service
                              (app.core_service, persistent process)
                                          |
                    ResourceManager (state machine, one load per process)
                                          |
                         EvidenceReportService (existing V0.3.2 pipeline)
                                          |
                    UnifiedSearchService / SemanticIndex / LocalEmbedder
                                          |
                              data/literature.db, data/semantic/
```

`app.core_service.evidence_gateway` is the single place `find_evidence`
input validation, evidence_types filtering, and report shaping happen.
Both the Core's HTTP handler and (indirectly, over HTTP) the MCP proxy go
through it; neither reimplements it.

## Lifecycle

`app.core_service.state.CoreState`: `STARTING -> LOADING -> READY`, or
`-> ERROR` if any step fails. `app.core_service.resource_manager.ResourceManager`
owns this: construction is free of I/O; `start_background_init()` runs the
checks (database, semantic index files, embedder load) on a daemon thread
and is idempotent - a second call is a no-op, so concurrent callers can
never trigger two loads. `search_service` and `status()` are safe to read
from any thread at any time.

## HTTP API

Loopback only (`127.0.0.1`), stdlib `http.server.ThreadingHTTPServer` - no
new dependency.

- `GET /health` - `{"ok": true}`. Never touches the database, index or
  model; always fast.
- `GET /status` - `{"state", "database_ready", "semantic_index_ready",
  "embedding_model_ready", "paper_count", "error"?}`. No filesystem paths.
- `POST /find_evidence` - `{"query", "top_k", "evidence_types"}` ->
  the existing `FindEvidenceResult` schema (`app.external_api.mcp_schemas`,
  unchanged and reused, not duplicated). Returns 503
  `{"error": "ResearchAssistantLoading", ...}` while `LOADING`, or
  `{"error": "ResearchAssistantUnavailable", ...}` if `ERROR`.

## Service discovery and single instance

`app.core_service.discovery`:
- A lock file (`data/core_service.lock`) whose OS-level exclusive lock
  (`msvcrt.locking` on Windows) is the actual single-instance guard -
  atomic, so it closes the race a health-check-then-bind sequence alone
  cannot. A crash releases it automatically (the OS does it).
- A discovery file (`data/core_service.discovery.json`): `{host, port,
  pid, started_at}`, written after the port is bound. This is what lets a
  dynamic (OS-assigned) fallback port work: callers read this file and
  probe `/health`, never assume a fixed port.

Startup order: acquire the lock (exit cleanly, reporting the existing Core,
if another process already holds it) -> bind the configured default port
(`RESEARCH_ASSISTANT_CORE_PORT`, default 8756) or fall back to an
OS-assigned port on collision -> write the discovery file -> start
background init -> serve.

## MCP as a thin proxy

`app.external_api.mcp_adapter` no longer imports `EvidenceReportService`,
`UnifiedSearchService`, `SemanticIndex`, or `LocalEmbedder`. It calls
`app.core_service.client.CoreClient`, which discovers the Core via
`app.core_service.discovery` and forwards the request over HTTP. If no
running, healthy Core is found, it raises `ResearchAssistantUnavailableError`
- it never falls back to loading the Evidence Engine itself. Restarting
the MCP process (or Claude Code) never touches the Core, so the embedder
is never reloaded because of an MCP restart.

## Configuration

`app.config.APP_DATA_DIR` (override: `RESEARCH_ASSISTANT_DATA_DIR`) is the
one seam for a future packaged install; `DATABASE_PATH`,
`CORE_DISCOVERY_FILE` and `CORE_LOCK_FILE` are derived from it.
`CORE_SERVICE_DEFAULT_PORT` is overridden by `RESEARCH_ASSISTANT_CORE_PORT`.
Development defaults are unchanged (project `data/` directory).

## Running it

```
.venv\Scripts\python.exe -m app.core_service        # start the Core (once)
.venv\Scripts\python.exe -m app.external_api.mcp_server   # MCP proxy, any time, any number of restarts
```

## Known V0.5 limitations (deferred, see brief section 19)

No Windows installer, system tray UI, or auto-start on login. The desktop
GUI still constructs its own `DesktopSearchService` directly - not yet
migrated to the Core (a small, deliberate seam for that migration is the
`app.core_service.client.CoreClient` shape, but the GUI itself is
untouched in V0.5). No local auth token yet (loopback-only binding is the
current security boundary).
