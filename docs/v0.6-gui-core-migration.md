# Desktop GUI -> Research Assistant Core migration (V0.6)

## Why

V0.5 introduced the persistent Research Assistant Core Service so the MCP
proxy would never reload the BGE embedder on restart. The desktop GUI,
however, still built its own `UnifiedSearchService` directly and, for any
non-keyword search or Evidence Pack, shelled out to a fresh
`app.search.desktop_search` subprocess that reloaded the embedder from
scratch on every single call. V0.6 makes the GUI a client of the same
persistent Core instead, so there is exactly one heavy-resource owner in
the whole system - Core, GUI and MCP all reuse the one loaded model.

## Architecture

```
Desktop GUI (app.ui.main_window.MainWindow)
        |
        |-- app.ui.core_process_manager.CoreProcessManager   (detect/start Core)
        |-- app.ui.core_process_manager.CoreMonitor          (poll lifecycle, off GUI thread)
        |-- app.ui.core_search_adapter.CoreSearchAdapter     (thin adapter -> CoreClient)
        v
app.core_service.client.CoreClient  (the one HTTP client; also used by MCP)
        |  127.0.0.1 only
        v
Research Assistant Core Service (persistent process, unchanged from V0.5)
        |-- GET  /health, /status                  (unchanged)
        |-- POST /find_evidence                     (unchanged - MCP compatibility)
        |-- POST /search           (V0.6 - app.core_service.search_gateway)
        |-- POST /evidence_pack    (V0.6 - app.core_service.search_gateway)
        v
ResourceManager's shared UnifiedSearchService / EvidenceService / EvidenceReportService
```

`app.search.desktop_search.DesktopSearchService` and its per-call
subprocess are retired from the production GUI path - kept only because
`tests/test_desktop_search.py` still exercises the module.

## Core API additions

Both new endpoints delegate to the Core's one shared, already-loaded
`UnifiedSearchService`/`EvidenceService` (via `search_gateway.py`); neither
duplicates retrieval or evidence-pack logic, and neither is used by MCP.

- `POST /search` - `{"query", "mode": "keyword"|"semantic"|"hybrid",
  "top_k", collection?, year_min?, year_max?, journal?, paper_id?,
  result_level?, max_chunks_per_paper?, diversify_results?}` ->
  `{"results": [...]}`, one dict per `HybridResult` (`dataclasses.asdict`
  shape) - the same data the old per-call subprocess used to return.
- `POST /evidence_pack` - `{"query", collection?, year_min?, year_max?,
  journal?, max_papers?, max_passages_per_paper?, candidate_pool?}` ->
  `{"pack": {...}}`, the same shape `EvidencePack.to_dict()` always
  produced.

Both are gated on Core state exactly like `/find_evidence` (503
`ResearchAssistantLoading`/`ResearchAssistantUnavailable` while not
READY) - deliberately, so Keyword mode now also waits for the Core to be
fully ready rather than the old always-available local path. See
"Known trade-off" below.

## GUI lifecycle

`MainWindow` no longer constructs `DesktopSearchService`/
`UnifiedSearchService` itself. On startup (`auto_connect_core=True`, the
default):

1. `CoreProcessManager.ensure_core_running()` - reuses V0.5's
   `app.core_service.discovery` to find a healthy Core; if none exists,
   spawns `python -m app.core_service` and polls the discovery file until
   it is reachable (or gives up after 20s). Never starts a second Core if
   one is already found - the actual single-instance guard is the Core's
   own OS-level lock (V0.5); the GUI launcher does not duplicate it.
2. `CoreMonitor` runs that check, then polls `/status`, on a plain daemon
   thread (the same pattern `app.ui.worker.Worker` already uses for
   "search" tasks), emitting a Qt signal back to the GUI thread for each
   state: `UNAVAILABLE` (GUI-local pseudo-state - no Core could be found
   or started) / `STARTING` / `LOADING` / `READY` / `ERROR`.
3. `MainWindow._core_state_changed` updates a dedicated "Core · ..." label,
   shows a clear non-blocking message while `LOADING`
   ("Research Assistant is preparing the semantic model..."), and
   disables the search/evidence action until `READY`. The GUI window
   itself is visible and responsive throughout - nothing blocks on Core
   startup.
4. Once `READY`, `MainWindow.search_service` becomes a
   `CoreSearchAdapter` bound to the discovered Core; before that, and
   whenever the Core is `UNAVAILABLE`/`ERROR`, it stays `None` and no
   local fallback is ever constructed.

GUI shutdown (`closeEvent`) stops `CoreMonitor`'s own signal emission
(so a background poll never reaches into a destroyed window) but never
touches the Core process - Claude/Codex or another GUI instance may still
be using it. There is no "stop the Core" method anywhere in
`CoreProcessManager`/`CoreMonitor`.

## Search mode mapping

| GUI mode | Core endpoint | Notes |
| --- | --- | --- |
| Search / Keyword | `POST /search`, `mode=keyword` | previously ran in-process, now via Core too (see trade-off) |
| Search / Semantic | `POST /search`, `mode=semantic` | previously a per-call subprocess |
| Search / Hybrid | `POST /search`, `mode=hybrid` | previously a per-call subprocess |
| Evidence Pack | `POST /evidence_pack` | previously a per-call subprocess; same `EvidencePack` shape and rendering |
| Evidence Report (new) | `POST /find_evidence` (unchanged) | new mode; shows the V0.3+ classified, citation-traced report |

## Evidence Report UI

A third `app_mode`, "Evidence Report", added alongside the existing
"Search" and "Evidence Pack". It renders a plain, read-only, grouped text
report (`MainWindow._format_evidence_report`) - DIRECT / SECONDARY /
LIMITING / CONTEXTUAL / UNCERTAIN sections, each item showing paper title,
journal/year/DOI, Zotero key, PDF page, rationale, citation-trace status,
and the exact passage - plus a "Copy Evidence Report" button. No card
redesign, per the brief's explicit minimalism.

## Known, disclosed trade-off

Because `/search` is gated on full Core `READY` (database + semantic
index + embedding model all loaded) exactly like `/find_evidence`, Keyword
mode - which never itself needed the semantic model - now also waits for
the Core to finish loading, whereas the old GUI could keyword-search
immediately even before any semantic index existed. This was a deliberate
simplification (uniform gating, one readiness definition, no special-cased
partial-readiness logic) rather than an oversight; it trades a small
regression in keyword-only responsiveness on a cold Core for a
substantially simpler, more consistent lifecycle model.

## Packaging / configuration

Nothing new: the GUI launcher uses the same `app.config`/
`app.core_service.discovery` seams V0.5 already introduced
(`RESEARCH_ASSISTANT_DATA_DIR`, `RESEARCH_ASSISTANT_CORE_PORT`, the
discovery file). No developer-specific path is hard-coded in production
code.
