# V0.4.1: MCP connectivity, startup diagnostics, and Windows client integration

V0.4-A shipped a working `find_evidence` MCP server (`app/external_api/`), but
the real Claude Code client never showed `research-assistant-evidence` under
`/mcp`. This release does not touch the Evidence Engine or `find_evidence`'s
behavior; it only fixes and hardens how the server is discovered, launched,
and diagnosed on Windows.

## Root causes found

1. **No MCP registration existed anywhere.** There was no project-level
   `.mcp.json` (not at the `research-assistant` repo root, not at the parent
   workspace folder), and no entry in the user-level Claude Code config
   (`~/.claude.json`). `docs/v0.4-mcp.md` only ever showed an example config -
   nothing had actually created it. This alone fully explains `/mcp` showing
   nothing: Claude Code had zero configuration pointing at this server.

2. **The example config in `docs/v0.4-mcp.md` used an unsupported `cwd`
   field.** Inspecting the installed Claude Code VS Code extension's own
   config schema (`claude-code-settings.schema.json` and the bundled
   `extension.js`, version 2.1.274) shows the stdio MCP server shape actually
   accepted is:

   ```text
   { type?: "stdio", command: string, args?: string[], env?: Record<string,string>,
     timeout?: number, alwaysLoad?: boolean, role?: ... }
   ```

   There is **no `cwd` key**. Even if a `.mcp.json` with a `cwd` field had
   existed, Claude Code would have silently ignored it and launched the
   server with its own working directory (the open workspace folder, e.g.
   `C:\path\to\workspace`) - not the `research-assistant`
   project root.

3. **`-m app.external_api.mcp_server` cannot resolve without the project root
   on `sys.path`.** This was reproduced directly: running the module from the
   parent folder fails immediately with `ModuleNotFoundError: No module named
   'app'` (Python's own `-m` machinery resolves the module before any
   application code runs, so nothing inside `mcp_server.py` can fix this
   case). Since `.mcp.json` has no `cwd` field, this is a real, load-bearing
   problem, not a hypothetical - it is fixed with `env.PYTHONPATH` (below),
   confirmed working end-to-end in `tests/test_mcp_startup.py`.

What was **not** the problem:

- `app.config.DATABASE_PATH` and the semantic index directory already resolve
  from `Path(__file__)`, not from the process's current working directory -
  they were already portable and contain no hard-coded username.
- stdout hygiene was already correct: `mcp_server.py` sends all logging to
  `stderr`, and nothing in the `find_evidence` import chain (`mcp_adapter` ->
  `EvidenceReportService` -> ... ) imports the CLI-only modules that do
  `print()` (`app/cli.py`, `app/search/evaluate_retrieval.py`,
  `app/search/semantic_poc.py`). Verified with a real end-to-end
  `find_evidence` call and OS-level stdout capture on the subprocess (not
  just Python-level `sys.stdout` patching, which a C extension could bypass).

## What changed

- **`app/external_api/mcp_server.py`**: added a `sys.path` bootstrap (active
  only when the module is *not* imported as a package, i.e. run as a direct
  script rather than via `-m`) that inserts the project root computed from
  `Path(__file__).resolve().parents[2]`. Added non-fatal, stderr-only startup
  warnings when `literature.db` or the semantic index is missing/incomplete
  (the server still starts and still advertises `find_evidence` either way -
  a missing local index is a `find_evidence`-time `DatabaseUnavailableError`,
  not a reason to refuse to start).
- **`app/external_api/mcp_diagnostics.py`** (new): a read-only, human-readable
  diagnostic CLI - see below. Never opens the database read-write, so it
  never creates `literature.db` as a side effect of checking it.
- **`.mcp.json`** (new, at the workspace root
  `C:\path\to\workspace\.mcp.json`): the canonical project
  MCP config (below).
- **Tests**: `tests/test_mcp_diagnostics.py`, `tests/test_mcp_startup.py`
  (new). No existing test was modified.

## Diagnostic command

Read-only; never modifies Zotero, `literature.db`, the semantic index, or any
PDF. Exit code `0` on success, `1` if any check fails.

```powershell
C:\path\to\research-assistant\.venv\Scripts\python.exe -m app.external_api.mcp_diagnostics
```

It checks (in order): the Python executable/version, the project root, every
`requirements.txt` dependency, whether `app.external_api.mcp_server` and
`EvidenceReportService` import, whether `literature.db` exists *and* is
readable (via a `mode=ro` SQLite connection - it cannot create the file),
whether the semantic index's three files exist, and finally runs one real,
read-only `EvidenceReportService.build_report` call as an end-to-end smoke
test.

This is a separate, ordinary CLI tool - it is allowed to print to stdout
because it is never wired up as an MCP server in `.mcp.json`.

## `.mcp.json` (canonical, project-scoped)

```json
{
  "mcpServers": {
    "research-assistant-evidence": {
      "type": "stdio",
      "command": "C:\\path\\to\\research-assistant\\.venv\\Scripts\\python.exe",
      "args": ["-m", "app.external_api.mcp_server"],
      "env": {
        "PYTHONPATH": "C:\\path\\to\\research-assistant"
      }
    }
  }
}
```

`env.PYTHONPATH` (not `cwd`, which this Claude Code version does not support
for MCP servers) is what makes `-m app.external_api.mcp_server` resolve the
`app` package regardless of what working directory Claude Code actually
launches the process from. This has been verified end-to-end (see
`tests/test_mcp_startup.py::RealStdioSubprocessTests`, and manually against
this exact file - see Verification below).

If your Claude Code project root is the `research-assistant` folder itself
(rather than its parent workspace folder), put this same file at
`research-assistant\.mcp.json` instead - project-scoped `.mcp.json`
discovery is tied to whichever folder Claude Code considers the project root.

## Claude Code CLI registration

**Not verified in this environment**: no standalone `claude` executable is on
`PATH` in this shell (checked in both the Bash tool and PowerShell) or as a
global npm package. The only Claude Code present is the VS Code extension
that is running this very session. The commands below reflect Claude Code's
documented CLI, for use on a machine/shell where `claude` is installed
separately - they have not been executed here.

Scope matters:

- **Project scope** (`--scope project`) writes to the project's `.mcp.json`,
  intended to be shared/committed with the repo. **Use this one** for
  Research Assistant, since `.mcp.json` above is meant to be the checked-in,
  canonical config for anyone working in this repo.
- **Local scope** (`--scope local`, the CLI default if `--scope` is omitted)
  is per-user, per-project, and not committed - useful only if you want a
  personal override that differs from the project's `.mcp.json`.
- **User scope** (`--scope user`) applies across all of a user's projects -
  not appropriate here, since this server is specific to this one local
  Zotero library/database.

```powershell
# Add (project scope - writes/updates .mcp.json):
claude mcp add research-assistant-evidence --scope project `
  --env PYTHONPATH=C:\path\to\research-assistant `
  -- C:\path\to\research-assistant\.venv\Scripts\python.exe `
     -m app.external_api.mcp_server

# List all configured MCP servers (all scopes):
claude mcp list

# Inspect this one server's resolved config:
claude mcp get research-assistant-evidence

# Remove it (e.g. before re-adding with different settings):
claude mcp remove research-assistant-evidence --scope project

# Re-add after removing:
claude mcp add research-assistant-evidence --scope project `
  --env PYTHONPATH=C:\path\to\research-assistant `
  -- C:\path\to\research-assistant\.venv\Scripts\python.exe `
     -m app.external_api.mcp_server
```

Claude Code requires the user to approve a project's `.mcp.json` servers the
first time they're seen in a given project directory. If `/mcp` still doesn't
show `research-assistant-evidence` after adding the file, check for an
approval/trust prompt in Claude Code for this project, or reset that
project's remembered MCP choices per Claude Code's own documentation for your
installed version - the exact command for this was not confirmed in this
environment (see above).

Do not rely on public MCP registry discovery for this server: it is a custom,
purely local tool over the user's own `data/literature.db`, not something
published for other users to find.

## One-command verification workflow

Run these in order after any change to `.mcp.json` or the server:

**A. Diagnostics** (confirms environment/dependencies/data, independent of
Claude Code entirely):

```powershell
C:\path\to\research-assistant\.venv\Scripts\python.exe -m app.external_api.mcp_diagnostics
```

**B. Launch/smoke-test the actual MCP module** (confirms the stdio process
itself starts and stays up rather than crashing - it will appear to hang,
which is correct: it is waiting for a client on stdin, not idle/broken; press
Ctrl+C to stop it):

```powershell
C:\path\to\research-assistant\.venv\Scripts\python.exe -m app.external_api.mcp_server
```

**C. Check Claude Code MCP registration** (only if a standalone `claude` CLI
is available in your shell):

```powershell
claude mcp list
claude mcp get research-assistant-evidence
```

**D. Open Claude Code in the project.**

**E. Check `/mcp`** and confirm `research-assistant-evidence` is listed and
connected.

**F. Run one real query** through Claude Code itself (not this repo's test
suite):

```
In2Se3 phase change by strain
```

Expected flow: Claude Code -> `find_evidence` -> `app.external_api.mcp_adapter`
-> `EvidenceReportService` -> the real `data/literature.db` -> structured
Zotero-backed evidence in the response. No evidence content is hard-coded
anywhere in this release; what comes back depends entirely on what's actually
in the user's indexed Zotero library.

## Explicitly out of scope (unchanged architecture)

Claude Code must never connect to Zotero directly. The only path is, and
remains:

```
Claude Code -> research-assistant-evidence (this MCP server)
             -> app.external_api.mcp_adapter
             -> EvidenceReportService
             -> data/literature.db + data/semantic/ (already indexed from Zotero)
```

No Zotero Web API, Zotero local HTTP API, Zotero MCP server, or web search
was added. No new tools (`get_source`, `find_evidence_for_claim`,
`verify_citation`, etc.) were added. `find_evidence` is unchanged.
