# V0.7 Scientific Evidence Inspection and Citation Verification

V0.7 extends the V0.6 persistent-Core architecture. The GUI and MCP server remain
lightweight clients; the Core remains the only owner of the Evidence Engine,
semantic index, and embedding model. All operations are read-only.

## Public tools

### `find_evidence`

Searches the local library for classified evidence. Its existing response remains
compatible and now also includes an opaque `report_id`. Each item retains its
report-local `evidence_id`.

### `find_evidence_for_claim`

Input:

```json
{"claim": "Mechanical strain can induce phase transitions in In2Se3.", "top_k": 10}
```

The exact claim is passed to the existing Evidence Engine without LLM rewriting.
The response includes `report_id`, retrieval counts, and the normal classified
items grouped as `direct_support`, `limiting`, `secondary`, `contextual`, and
`uncertain`. Citation traces remain attached to secondary items; independently
retrieved and classified primary evidence remains a separate item.

### `get_source`

Input:

```json
{"report_id": "evr_...", "evidence_id": "E3", "context_pages": 1}
```

`context_pages` may be 0, 1, or 2. The Core resolves the handle to its cached
Zotero item key, attachment key, and physical PDF page, then reads original page
text from `literature.db`. It does not run a search or read a caller-supplied path.
The response separates `source.evidence_passage` from surrounding `source.pages`
and a page-delimited `source.text`. `start_page`, `end_page`, and `status` keep
page boundaries auditable.

### `verify_citation`

Input:

```json
{"claim": "Mechanical strain can induce phase transitions in In2Se3.",
 "report_id": "evr_...", "evidence_id": "E3"}
```

The Core reuses the production deterministic classifier on the exact supplied
claim and stored passage. It returns one of:

- `SUPPORTED`
- `SECONDARY_SUPPORT_ONLY`
- `LIMITS_OR_CONTRADICTS`
- `NOT_SUPPORTED`
- `INSUFFICIENT_CONTEXT`

The response also gives the Evidence Engine class, source type, and structured
claim/material/stimulus/phase matches. It does not accept fabricated paper
metadata and does not perform an unrelated search.

## Handle lifecycle

The persistent Core owns a thread-safe, bounded in-memory cache. Defaults are a
one-hour TTL and 100 reports; deployments can set
`RESEARCH_ASSISTANT_REPORT_TTL_SECONDS` and
`RESEARCH_ASSISTANT_REPORT_MAX_COUNT`. Capacity eviction and TTL expiration leave
bounded tombstones so a recently expired handle produces `ReportExpired` rather
than resolving incorrectly. MCP restarts do not affect handles, but a Core restart
invalidates all handles. Reports are never persisted to disk.

`evidence_id` is unique only inside its report. Agents must use IDs returned by an
evidence call and must never fabricate them.

## Core HTTP API

All scientific operations use POST, matching the existing request-body convention:

- `/find_evidence` (backward compatible; adds `report_id`)
- `/find_evidence_for_claim`
- `/source`
- `/verify_citation`

Existing `/health`, `/status`, `/search`, and `/evidence_pack` behavior is unchanged.

Structured errors include `ReportNotFound`, `ReportExpired`, `EvidenceNotFound`,
`SourceContextUnavailable`, `InvalidClaim`, and `CitationVerificationError`, in
addition to existing Core errors. Failures are not returned as empty successes.

## Interpretation and limitations

Evidence classification describes how a retrieved passage relates to a query.
Citation verification conservatively checks one known passage against one exact
claim using the same deterministic match fields. Classification confidence is
confidence in the class assignment, not a probability that a claim is true.

Research Assistant does not determine scientific truth. It determines whether
the locally available evidence supports, limits, or does not support a supplied
claim. It uses no general-purpose LLM, web search, external metadata API, journal
ranking, or manuscript-writing system in V0.7.
